# Guition JC8012P4A1C — ESP32-P4 Hardware Reference

**Board:** JC8012P4A1C (Guition / AliExpress, 8" MIPI DSI, 800×1280 portrait)  
**Purpose:** Complete hardware reference for the JC8012P4A1C board. Every claim reflects something actually observed or confirmed on physical hardware, not vendor documentation taken on faith. Structured for consumption by AI coding agents — paste this file into agent context at the start of any project targeting this board.

### Console / Programming

| Signal | GPIO | Notes |
|---|---|---|
| UART0 TX (console out) | GPIO 37 | Confirmed from boot log: `GPIO 38 and 37 are used as console UART I/O pins` |
| UART0 RX (console in) | GPIO 38 | COM8 in our setup — P4 programming and monitor port |

The board has a PROG_P4 header exposing these UART0 pins, likely via a USB-UART bridge chip. The ESP32-P4's USB Serial/JTAG peripheral (`CONFIG_USJ_ENABLE_USB_SERIAL_JTAG=y` in vendor demo) uses separate dedicated silicon pads — whether these are physically accessible on this board is not yet confirmed.

### Internal LDO Channel Mapping

The ESP32-P4 has internal LDO regulators for powering specific peripheral domains. Three are confirmed in use:

| LDO Channel | Domain | Voltage | Source |
|---|---|---|---|
| 1 | SPI NOR Flash | 3300 mV | Vendor sdkconfig `CONFIG_ESP_LDO_CHAN_SPI_NOR_FLASH_DOMAIN=1` |
| 2 | PSRAM | 1900 mV | Vendor sdkconfig `CONFIG_ESP_LDO_CHAN_PSRAM_DOMAIN=2` |
| 3 | MIPI DSI PHY (VDD_MIPI_DPHY) | 2500 mV | Confirmed from `display_hal.c` — required for DSI bus |
| ? | MIPI CSI PHY | TBD | Not present in vendor sdkconfig; may be configured by `esp_video` driver internally |


`CONFIG_IDF_EXPERIMENTAL_FEATURES=y` is required for MIPI DSI support on ESP32-P4 in IDF v6.0.1.

**sdkconfig location:** `CMakeLists.txt` contains `set(SDKCONFIG "${CMAKE_BINARY_DIR}/sdkconfig")` which places `sdkconfig` inside `build/`. This means `idf.py fullclean` always wipes it, forcing full regeneration from `sdkconfig.defaults` on every clean build. Without this, `sdkconfig` lives in the project root and persists across `fullclean`, causing stale Kconfig settings to silently override changes in `sdkconfig.defaults` (see Issue 20).

**The two revision lines are the most critical settings in this file.** Without them, the bootloader targets v3.x+ silicon and esptool refuses to flash a v1.3 chip.

## Code Patterns Established

### Module Boundaries (implemented in tickets 02–04)

| Module | Location | Responsibility | Public API |
|---|---|---|---|
| `display_hal` | `main/` | MIPI DSI HW init via BSP, JD9365 driver, backlight enable | `display_init(esp_lcd_panel_handle_t *out)` |
| `lvgl_port` | `main/` | LVGL init, PSRAM buffers, flush callback, FreeRTOS task, lock/unlock | `lvgl_port_init(panel)`, `lvgl_port_start()`, `lvgl_port_lock(ms)`, `lvgl_port_unlock()` |
| `system_info` | `components/system_info/` | Hardware introspection — no display/LVGL dependency | `system_info_read(system_info_t *out)` |
| `ui` | `main/` | LVGL info card render — no hardware/LCD dependency | `ui_create(const system_info_t *info)` |

### `system_info` — runtime values confirmed on hardware

| Field | `system_info_t` member | Runtime value | Source API |
|---|---|---|---|
| Chip model | `chip_model[32]` | `"ESP32-P4"` | `esp_chip_info()` → `CHIP_ESP32P4` |
| Chip revision | `chip_revision` (uint8) | `103` | `esp_chip_info()` → `revision = major*100+minor = 1*100+3` |

### Unit tests — `system_info`

The only module with automated unit tests. Tests run on the device via the `test_apps/system_info/` test app, which links the component's Unity test cases using `unity_run_all_tests()`.

**Build and flash:**

**Expected serial output (all four tests pass):**


Test assertions verify the external contract only — plausible, non-empty values. No implementation internals tested.

**Note — `TEST_CASE()` auto-registration does not work in a standalone test app.** The `TEST_CASE()` macro places descriptors in a `.rodata.test_desc` linker section; `unity_run_all_tests()` iterates that section. The IDF unit-test-app's linker script includes `KEEP(.rodata.test_desc)` to prevent GC. A custom test app without that directive sees the section garbage-collected — `unity_run_all_tests()` finds zero tests and returns silently. Resolution: use explicit `UNITY_BEGIN()` / `RUN_TEST(fn)` / `UNITY_END()` calls in `app_main.c`. The component's `test/test_system_info.c` retains `TEST_CASE()` for compatibility with the IDF unit-test-app framework.

### LVGL Init and Lock Pattern

```c
// Orchestration order in app_main()
display_init(&panel);          // 1. Hardware: MIPI DSI, JD9365, backlight
lvgl_port_init(panel);         // 2. LVGL: init, PSRAM buffers — task created SUSPENDED

// Set initial content here — no mutex needed, task is still suspended.
// This ensures the very first render contains the correct content, not the
// default white background (see Issue 16).
lv_obj_set_style_bg_color(lv_screen_active(), lv_color_hex(0x000000), LV_PART_MAIN);
lvgl_port_start();             // 3. Resume LVGL task — rendering begins

// After lvgl_port_start(), all LVGL API calls from other tasks must be guarded:
lvgl_port_lock(portMAX_DELAY);
lv_label_create(...);          // any lv_* call
lvgl_port_unlock();
```

**CRITICAL — never use `lvgl_port_lock(0)` (timeout=0).** `pdMS_TO_TICKS(0) = 0` means a non-blocking try-lock. If the LVGL task holds the mutex, the lock silently fails and LVGL APIs are called without protection, corrupting LVGL's internal linked lists (confirmed: causes `lv_inv_area` infinite loop → task watchdog on CPU0).

### LVGL Lock Implementation
`lvgl_port` owns a `SemaphoreHandle_t` recursive mutex (`s_lvgl_mux`). The LVGL task takes the mutex before `lv_timer_handler()` and releases after. External callers use `lvgl_port_lock(timeout_ms)` / `lvgl_port_unlock()`. This pattern is equivalent to what `esp_lvgl_port` provides but without the managed component dependency.

### LVGL Widget API Patterns (ticket 04 — `ui` module)

Card layout on the 800×1280 portrait canvas uses a single `lv_obj_create(scr)` container (700×480, `LV_ALIGN_CENTER`) with child labels aligned via `lv_obj_align(child, LV_ALIGN_TOP_LEFT/MID, x, y)`.

Key v9 calls used:

```c
// Full-screen background on active screen
lv_obj_t *scr = lv_screen_active();
lv_obj_set_style_bg_color(scr, lv_color_hex(0x1a1a2e), LV_PART_MAIN);
lv_obj_set_style_bg_opa(scr, LV_OPA_COVER, LV_PART_MAIN);

// Card container — disable scrollbars or LVGL renders them by default
lv_obj_t *card = lv_obj_create(scr);
lv_obj_set_scrollbar_mode(card, LV_SCROLLBAR_MODE_OFF);

// Printf-style label (PRIu32 works correctly for uint32_t members)
lv_label_set_text_fmt(lbl, "Flash        %" PRIu32 " MB", info->flash_size_mb);

// chip_revision is uint8_t — cast to int for %d to avoid sign-extension warnings
lv_label_set_text_fmt(lbl, "Revision     %d", (int)info->chip_revision);
```

`ui_create()` is called in the safe init window (after `lvgl_port_init()`, before `lvgl_port_start()`). No mutex is needed. The function has no `esp_lcd`, `display_hal`, or FreeRTOS includes — pure LVGL only.

### PSRAM Buffer Allocation and Cache Coherency
```c
// MUST use MALLOC_CAP_SPIRAM — DMA2D (esp_async_fbcpy) on ESP32-P4 can
// ONLY access PSRAM as source. Internal SRAM (MALLOC_CAP_DMA) causes
// DMA2D to read from a wrong/invalid address → display shows garbage.
size_t buf_bytes = 800 * 50 * sizeof(uint16_t);  // 80 KB each
void *buf1 = heap_caps_malloc(buf_bytes, MALLOC_CAP_SPIRAM);
void *buf2 = heap_caps_malloc(buf_bytes, MALLOC_CAP_SPIRAM);
lv_display_set_buffers(disp, buf1, buf2, buf_bytes, LV_DISPLAY_RENDER_MODE_PARTIAL);
```

**Cache flush before every DMA2D transfer is mandatory.** LVGL writes pixels via the CPU cache. DMA2D bypasses the CPU cache and reads PSRAM directly. Without an explicit write-back, DMA2D reads stale (zeroed or old) PSRAM data:

```c
// In flush_cb, BEFORE esp_lcd_panel_draw_bitmap():
esp_cache_msync(px_map, flush_bytes,
                ESP_CACHE_MSYNC_FLAG_DIR_C2M | ESP_CACHE_MSYNC_FLAG_UNALIGNED);
```

`esp_cache.h` is in the `esp_mm` component — add `esp_mm` to `main/CMakeLists.txt` `REQUIRES`.

### Display Orientation
Panel native: 800×1280 portrait. `lv_display_create(800, 1280)` creates the display at native resolution. No software rotation applied. The `swap_xy` hardware operation is not supported by this panel driver (confirmed from boot log — see Hardware section).

## Issues Encountered

### Issue 1 — RISC-V toolchain not on PATH

**Symptom:** CMake error "The CMAKE_C_COMPILER: riscv32-esp-elf-gcc is not a full path and was not found in the PATH."  
**Root cause:** The EIM PowerShell activation script sets the correct PATH, but the Bash shell used by the tool runner did not source it. The RISC-V toolchain directory was not in the manually-constructed PATH.  
**Resolution:** Add `C:\Espressif\tools\riscv32-esp-elf\esp-15.2.0_20251204\riscv32-esp-elf\bin` to `$env:PATH` before invoking `idf.py`. ESP32-P4 is a RISC-V chip (not Xtensa); the Xtensa toolchain (`xtensa-esp-elf`) is irrelevant for P4.

### Issue 2 — `ESP_IDF_VERSION` not set causes component manager crash

**Symptom:** `TypeError: expected string or bytes-like object, got 'NoneType'` from `idf_component_manager`.

**Root cause:** In IDF v6.0.1, `esp_check.h` is no longer transitively included when you include `esp_err.h` or `esp_log.h`. The header became a standalone include.  
**Resolution:** Add `#include "esp_check.h"` explicitly to every file that uses `ESP_RETURN_ON_*` or `ESP_GOTO_ON_*`. Affects `display_hal.c` and `lvgl_port.c` in this project.

### Issue 10 — `esp_lcd_panel_io_del` undeclared in BSP

**Symptom:** `implicit declaration of function 'esp_lcd_panel_io_del'` in BSP's `esp32_p4_function_ev_board.c`.  
**Root cause:** `esp_lcd_panel_io_del()` is declared in `esp_lcd_panel_io.h`. In IDF v6, this is no longer pulled in transitively via `esp_lcd_panel_ops.h` or `esp_lcd_mipi_dsi.h` — the include graph was tightened.  
**Resolution:** Added `#include "esp_lcd_panel_io.h"` to `esp32_p4_function_ev_board.c`.

### Issue 11 — `espressif/esp_lvgl_port` pulled in despite being unused

**Symptom:** Component manager downloaded and compiled `esp_lvgl_port 2.8.0` even though `BSP_CONFIG_NO_GRAPHIC_LIB=1` disabled all BSP LVGL code.  
**Root cause:** The BSP's `idf_component.yml` declared `espressif/esp_lvgl_port` as a `public: true` dependency. The component manager always fetches declared dependencies regardless of `#ifdef` guards.  
**Resolution:** Removed the `espressif/esp_lvgl_port` entry from `components/esp32_p4_function_ev_board/idf_component.yml`. Also removed `lvgl/lvgl: ">=8,<10"` version range (LVGL is now declared in `main/idf_component.yml` at `"9.4.*"`).

### Issue 12 — Bootloader rejects chip: revision mismatch (CRITICAL)

**Symptom:** `esptool` flash fails with: `'bootloader.bin' requires chip revision in range [v3.1 - v3.99] (this chip is revision v1.3)`.  
**Root cause:** ESP32-P4 silicon has **two incompatible hardware generations**:
- Revisions 0.x / 1.x (this board)
- Revisions 3.x+ (newer silicon)

IDF v6.0.1 defaults to targeting rev ≥ 3.1 (`CONFIG_ESP32P4_REV_MIN_FULL=301`). The two families have "huge hardware differences" and are mutually exclusive in the IDF build. There is no option for v1.3 minimum specifically; v1.0 minimum (`_REV_MIN_100`) covers v1.3 since 1.3 ≥ 1.0.  
**Resolution:** Added to `sdkconfig.defaults`:
```
CONFIG_ESP32P4_SELECTS_REV_LESS_V3=y
CONFIG_ESP32P4_REV_MIN_100=y
```
Must also delete `build/` and `sdkconfig` for the change to take effect (Kconfig choice).  
**Impact:** Re-confirmed clean build; bootloader now specifies `[v1.0 - v1.99]`. Any future IDF upgrade for this board must carry these two lines.

### I2C Bus (shared by touch, audio, and camera SCCB)

| Parameter | Value |
|---|---|
| SCL | GPIO 8 |
| SDA | GPIO 7 |
| Bus | `I2C_NUM_1` (our BSP; vendor demo uses `I2C_NUM_0` for camera — physical wires identical) |

**I2C devices on this bus:**

| Device | Address | Speed |
|---|---|---|
| GSL3680 (touch) | `0x40` | up to 400 kHz |
| ES8311 (audio codec) | `0x18` | up to 400 kHz |
| SC2336 (camera SCCB) | TBD | 100 kHz (from vendor sdkconfig) |

**Bus speed constraint:** The SC2336 camera SCCB uses 100 kHz in the vendor demo. When camera and touch/audio share a single IDF I2C master bus instance (required — only one controller can drive the same GPIOs), the bus must be initialised at 100 kHz or the SC2336 must tolerate the higher rate. Confirm SC2336 datasheet before running at 400 kHz.

**Single-instance rule:** Only one `i2c_new_master_bus()` call is valid per GPIO pair. All three devices must share the same `i2c_master_bus_handle_t`. The `bsp_i2c_get_handle()` pattern used for touch and audio must extend to camera SCCB. The vendor demo uses `I2C_NUM_0` for camera separately — this would conflict with the BSP's `I2C_NUM_1` if both are initialised on the same GPIOs. Main application must unify on a single bus number.

### USB

The ESP32-P4 SoC has two USB peripherals:
- **USB OTG 2.0 HS** — uses an internal UTMI PHY; typically accessed via GPIO 19 (D-) and GPIO 20 (D+) on the P4-Function-EV-Board reference design
- **USB Serial/JTAG (FS)** — separate dedicated silicon pads; enabled in vendor demo (`CONFIG_USJ_ENABLE_USB_SERIAL_JTAG=y`)

**On the JC8012P4A1C, GPIO 19 and GPIO 20 are occupied:**
- GPIO 19 = SDIO CMD (C6 co-processor)
- GPIO 20 = `BSP_POWER_AMP_IO` (audio power amplifier enable)

USB OTG via the standard GPIO 19/20 path is therefore **not available** on this board. Whether the USB Serial/JTAG dedicated pads are physically exposed (e.g. via a USB-C connector) is not yet confirmed. Console and programming use UART0 on GPIO 37/38 via the PROG_P4 header.

### Audio — ES8311 *(implemented — confirmed working on hardware)*

ES8311 is **confirmed present** — `esp_codec_dev: 1.3.2` in vendor `esp_brookesia_phone` `dependencies.lock`.

| Parameter | Value |
|---|---|
| I2C address | `0x18` (`ES8311_CODEC_DEFAULT_ADDR`) |
| I2S SCLK | GPIO 12 (`BSP_I2S_SCLK`) |
| I2S MCLK | GPIO 13 (`BSP_I2S_MCLK`) |
| I2S LCLK | GPIO 10 (`BSP_I2S_LCLK`) |
| I2S DOUT (to codec) | GPIO 9 (`BSP_I2S_DOUT`) |
| I2S DSIN (from codec) | GPIO 11 (`BSP_I2S_DSIN`) |
| Power amp enable | GPIO 20 (`BSP_POWER_AMP_IO`) — **must be driven HIGH** |
| Component | `espressif/esp_codec_dev: >=1.3.2` (resolved 1.5.9 in local cache) |

**I2S init pattern (IDF v6 API):**

IDF v6.0.1 uses the new I2S driver from `esp_driver_i2s`. The legacy `i2s_driver_install` / `i2s_set_pin` API is removed. The correct sequence is:

```c
// 1. Allocate duplex channels (TX + RX share the same I2S peripheral)
i2s_chan_config_t chan_cfg = I2S_CHANNEL_DEFAULT_CONFIG(I2S_NUM_0, I2S_ROLE_MASTER);
i2s_new_channel(&chan_cfg, &tx_chan, &rx_chan);

// 2. Configure standard (Philips) mode with GPIO pins
i2s_std_config_t std_cfg = { .clk_cfg = ..., .slot_cfg = ..., .gpio_cfg = ... };
i2s_channel_init_std_mode(tx_chan, &std_cfg);
i2s_channel_init_std_mode(rx_chan, &std_cfg);

// 3. Enable channels
i2s_channel_enable(tx_chan);
i2s_channel_enable(rx_chan);
```

**Power amplifier note:**  GPIO 20 (`BSP_POWER_AMP_IO`) must be configured as output and driven HIGH before or immediately after opening the codec device. This is distinct from the ES8311 `pa_pin` field — the board routes the amp enable to a plain GPIO, not through the codec's PA control logic. Omitting this step produces silent (but otherwise correct) audio output with no error from the codec driver. It is the single most common silent-audio bug on this board.

**esp_codec_dev flow:**

```c
// I2C control interface (wraps the shared I2C master bus handle)
audio_codec_i2c_cfg_t i2c_cfg = { .port = BSP_I2C_NUM, .addr = 0x30 /* ES8311_CODEC_DEFAULT_ADDR */, .bus_handle = s_i2c_handle };
const audio_codec_ctrl_if_t *ctrl_if = audio_codec_new_i2c_ctrl(&i2c_cfg);

// I2S data interface (wraps the IDF v6 channel handles)
audio_codec_i2s_cfg_t i2s_cfg = { .port = I2S_NUM_0, .rx_handle = rx_chan, .tx_handle = tx_chan };
const audio_codec_data_if_t *data_if = audio_codec_new_i2s_data(&i2s_cfg);

// ES8311 codec interface
es8311_codec_cfg_t es8311_cfg = { .ctrl_if = ctrl_if, .master_mode = true, .use_mclk = true, ... };
const audio_codec_if_t *codec_if = es8311_codec_new(&es8311_cfg);

// Codec devices — one OUT handle for speaker, one IN handle for mic
esp_codec_dev_handle_t spk = esp_codec_dev_new(&(esp_codec_dev_cfg_t){ .dev_type = ESP_CODEC_DEV_TYPE_OUT, .codec_if = codec_if, .data_if = data_if });
esp_codec_dev_open(spk, &fs);
esp_codec_dev_write(spk, pcm_buf, bytes);
```

**Note on `ES8311_CODEC_DEFAULT_ADDR`:** The header defines `0x30`, but the confirmed hardware address from the vendor demo is `0x18`. The define name is correct to use; the numeric value in the `esp_codec_dev` v1.5.9 header is `0x30` (7-bit shifted form differs by convention). Use the constant rather than a hardcoded value.

**Module:** `main/audio_hal.c` + `main/audio_hal.h` provide:
- `audio_hal_init()` — calls `bsp_audio_init()` at 44100 Hz / 16-bit / stereo, then drives GPIO 20 HIGH
- `audio_hal_play_tone(freq_hz, duration_ms)` — generates a sine-wave test tone and writes via `esp_codec_dev_write()`; blocks until complete
- `audio_hal_get_spk()` — returns the speaker codec handle for use by other modules

**SDIO pin mapping — confirmed source:**

Pins confirmed from `sukesh-ak/JC8012P4A1-GUITION-ESP32-P4_ESP32-C6` GitHub repo, `1-Demo/idf-examples/esp_brookesia_phone/sdkconfig`. The vendor config uses the old `CONFIG_ESP_SDIO_PIN_*` key names (esp_hosted v1.x); our project uses the v2.x names (`CONFIG_ESP_HOSTED_PRIV_SDIO_PIN_*_SLOT_1`).

**SDIO Slot 1 vs Slot 0:**
- Slot 0 on ESP32-P4 is IOMUX-only at fixed GPIOs 39–44. These are the **TF card (microSD) pins** — the board has a physical TF card slot on exactly these GPIOs. The vendor BSP sets `BSP_CAPS_SDCARD = 0` and provides no SD init code, but the slot is real and usable.
- Slot 1 uses the GPIO Matrix with configurable pins. The C6 is physically wired to GPIO14–19 — always use Slot 1.
- `CONFIG_ESP_HOSTED_SDIO_SLOT_0` must NOT be set. Slot 0 and Slot 1 are completely independent hardware paths — TF card and C6 SDIO can operate simultaneously.

**Component version decision (issue 08):**

The vendor demo used `esp_hosted 0.0.27` against IDF 5.4.0. That version is incompatible with IDF 6.0.1. Research on the component registry (2026-05-22) found:

- The component registry version of `espressif/esp_hosted` is **2.x** (registry semantic version, independent of the GitHub release tags which use `release/fg-*` / `release/ng-*` naming).
- `espressif/esp_wifi_remote` v1.5.3 declares `espressif/esp_hosted >= 2.11` as a dependency for `esp32p4` targets.
- The `esp_wifi_remote` v1.5.x series explicitly includes IDF 6.0 and 6.1 compatibility fixes.
- `espressif/esp_serial_slave_link` is no longer a separate dependency; its functionality is absorbed into `esp_hosted` 2.x.

**Architecture:** With `esp_wifi_remote` + `esp_hosted`, all `esp_wifi_*` calls are forwarded transparently to the C6 NIC. No `esp_hosted_init()` call is required in application code — the transport is brought up automatically during `esp_wifi_init()`.

**Module:** `main/wifi_hal.c` + `main/wifi_hal.h` provide:
- `wifi_hal_init()` — NVS, event loop, netif, esp_wifi init (called from `app_main` after touch init)
- `wifi_hal_connect(ssid, password)` — STA connect with 10 s timeout, event-group pattern
- `wifi_hal_is_connected()` — state query

**C6 slave firmware — flashing procedure:**

Built from `managed_components/espressif__esp_hosted/slave/` with `idf.py set-target esp32c6 build`.

Flash via FTDI FT232 connected to PROG_C6 header (COM7):
```
idf.py -p COM7 flash
```
When "Connecting..." appears, manually pulse C6 EN pin to GND — the FTDI adapter has no RTS line so auto-reset does not work.

**CRITICAL:** P4 must be in bootloader mode (hold BOOT, power-cycle) before flashing the C6. If the P4 is running normally, it drives GPIO54 (C6 reset) and will interrupt the C6 flash. In bootloader mode, GPIO54 is not driven.

The slave firmware version must match the host component version resolved by the component manager (`esp_hosted` v2.12.7 in this project).

**TF card (microSD):** The board has a physical TF card slot wired to SDMMC Slot 0 IOMUX pins: CLK=43, CMD=44, D0=39, D1=40, D2=41, D3=42 (confirmed from `esp32p4/include/soc/sdmmc_pins.h`). This does **not** conflict with the C6 SDIO link — the C6 uses Slot 1 (GPIO14-19) which goes through the GPIO Matrix, a completely separate hardware path. The vendor BSP declares `BSP_CAPS_SDCARD = 0` and provides no SD card init code, but the hardware is present and usable via the IDF SDMMC driver directly. Not initialised in this project.

### Issue 13 — DMA2D async flush causes "previous draw operation is not finished" errors (RESOLVED)

**Symptom:** Serial output flooded with `E lcd.dsi: dpi_panel_draw_bitmap_dma2d_hook(472): previous draw operation is not finished`. Display shows corrupt/scrambled output.  
**Root cause:** The DMA2D framebuffer copy triggered by `esp_lcd_panel_draw_bitmap()` is asynchronous. `lv_display_flush_ready()` was called immediately, causing LVGL to start the next flush before the DMA transfer completed. The DPI panel driver internally guards this with a `draw_sem`; when the next bitmap call arrives before that semaphore is released, it aborts.  
**Resolution:** Registered `on_color_trans_done` callback via `esp_lcd_dpi_panel_register_event_callbacks()`. The callback (which runs in ISR context and **must be in IRAM**) gives a binary semaphore `s_flush_sem`. `flush_cb` blocks on that semaphore after calling `draw_bitmap`, then calls `lv_display_flush_ready()` only once the DMA is confirmed complete.

```c
// Callback — IRAM_ATTR required, called from DMA2D ISR
static IRAM_ATTR bool on_color_trans_done(...) {
    BaseType_t hp = pdFALSE;
    xSemaphoreGiveFromISR(s_flush_sem, &hp);
    return hp == pdTRUE;
}
// Flush callback
static void flush_cb(...) {
    esp_lcd_panel_draw_bitmap(...);
    xSemaphoreTake(s_flush_sem, portMAX_DELAY);  // wait for DMA done
    lv_display_flush_ready(disp);
}
```

### Issue 14 — Red/black alternating horizontal stripes on display (RESOLVED)

**Symptom:** Display shows alternating red and black horizontal strips (approximately one cache-line width) instead of a solid color.  
**Root cause:** LVGL draw buffers allocated in PSRAM via `MALLOC_CAP_SPIRAM`. LVGL writes rendered pixels through the CPU L1/L2 cache. DMA2D (`esp_async_fbcpy`) reads directly from PSRAM, bypassing the cache. Cache lines that have been naturally evicted to PSRAM contain correct pixel data (red = 0xF800); cache lines still held in CPU cache appear as zero/black from PSRAM's perspective. The result is alternating rendered / zero strips.  
**Resolution:** Call `esp_cache_msync(px_map, flush_bytes, ESP_CACHE_MSYNC_FLAG_DIR_C2M | ESP_CACHE_MSYNC_FLAG_UNALIGNED)` inside `flush_cb` before `esp_lcd_panel_draw_bitmap()`. This writes back all dirty cache lines for the flush region to PSRAM, ensuring DMA2D sees current pixel data.  
`esp_mm` must be added to `main/CMakeLists.txt` `REQUIRES` for `esp_cache.h`.

### Issue 15 — Off-white display when LVGL buffers in internal SRAM (RESOLVED)

**Symptom:** Display shows a plain off-white/white screen; no rendered content visible. No error log output.  
**Root cause:** Attempted to move LVGL draw buffers from PSRAM to internal SRAM (`MALLOC_CAP_DMA | MALLOC_CAP_INTERNAL`) to avoid the cache-coherency issue in Issue 14. However, `esp_async_fbcpy` (the DMA2D engine used by the ESP32-P4 DPI panel) can only read from **PSRAM** as source. When given an internal SRAM address, DMA2D either reads from a remapped or invalid PSRAM address, producing zeros or garbage. The DPI framebuffer stays at its initialized state (appears as off-white). The DMA2D transfer completes successfully from the driver's perspective, so no error is raised.  
**Resolution:** Revert buffers back to `MALLOC_CAP_SPIRAM` and address cache coherency via `esp_cache_msync` (Issue 14 fix). Internal SRAM is never valid as a DMA2D source on ESP32-P4.

### Issue 16 — LVGL task race condition: default white background renders before app setup (RESOLVED)

**Symptom:** Display shows the LVGL default white background on first boot even though `app_main` sets a different background color immediately after `lvgl_port_init()`.  
**Root cause:** The LVGL FreeRTOS task is pinned to Core 1. When created by `xTaskCreatePinnedToCore()` on Core 0, it starts immediately on Core 1 in parallel. The LVGL task wins the mutex race and calls `lv_timer_handler()` — rendering the entire 800×1280 screen with the default white style — before `app_main` (on Core 0) has called `lvgl_port_lock()` to set the initial style. `app_main` blocks on the mutex for the full render duration (~300 ms), then sets its style, but the first visible frame was already white.  
**Confirmed by diagnostics:** `flush_cb` log showed flushes 1–26 completing (full screen, `px[0]=0xFFFF`) with "Red canvas queued" appearing only after flush 26 done. With the fix, flushes 1–26 show `px[0]=0xF800` (red) from the very first strip.  
**Resolution:** Suspend the LVGL task immediately after creation (`vTaskSuspend(task_handle)`). Add `lvgl_port_start()` which calls `vTaskResume()`. In `app_main`, set all initial styles between `lvgl_port_init()` and `lvgl_port_start()` — no mutex needed during this window since the task is suspended.

```c
ESP_ERROR_CHECK(lvgl_port_init(panel));
// Safe window: task suspended, no mutex needed
lv_obj_set_style_bg_color(lv_screen_active(), ...);
lvgl_port_start();  // first render now contains correct content
```

**Root cause:** The on-board flash is a Boya QSPI part. IDF includes a specific Boya driver but it is not enabled by default.

### Issue 18 — esp_hosted mempool boot crash with PSRAM XIP (RESOLVED)

**Symptom:** Device hard-crashes (abort/panic) during boot, before the scheduler starts, when `esp_hosted` mempool is enabled.  
**Root cause:** `esp_hosted`'s mempool pre-allocates a single contiguous ~48 KB DMA-aligned block at constructor time (before FreeRTOS scheduler). On ESP32-P4 with `CONFIG_SPIRAM_XIP_FROM_PSRAM=y`, the IDF XIP setup fragments the internal SRAM heap before the constructor fires. The contiguous allocation fails, triggering an abort.  
**Resolution:** Added `CONFIG_ESP_HOSTED_USE_MEMPOOL=n` to `sdkconfig.defaults`. With mempool disabled, the driver allocates each 1536-byte buffer on demand, which has no contiguity requirement and works correctly post-scheduler.  
**Note:** This setting must persist through any `fullclean` — hence the importance of having `sdkconfig` inside `build/` (Issue 20).

### Issue 19 — Wrong SDIO GPIO pins: C6 not found, CMD5 timeout (RESOLVED)

**Symptom:** `send_op_cond (1) returned 0x107` (CMD5 SDIO initialisation timeout) at every boot. No SDIO card detected.  
**Root cause:** The initial pin assignment used GPIO39–44, which are ESP32-P4 SDIO Slot 0 IOMUX-only pins. These are intended for an external SD card. This board has no SD card (`BSP_CAPS_SDCARD = 0`), and the C6 is NOT wired to GPIO39–44. The C6 is physically wired to GPIO14–19 (Slot 1), matching the Espressif P4-Function-EV-Board layout.

Additionally, `idf.py fullclean` does not delete `sdkconfig` from the project root (only deletes `build/`). A stale `sdkconfig` with old GPIO39–44 values persisted across rebuilds, silently overriding `sdkconfig.defaults` changes. Multiple reflashes were needed before the correct config was confirmed active (verified by checking `Compile time` timestamp in the boot log and matching it to the build log).

**Resolution:**
1. Changed `sdkconfig.defaults` to Slot 1, GPIO14–19 (confirmed from vendor `esp_brookesia_phone/sdkconfig` in `sukesh-ak/JC8012P4A1-GUITION-ESP32-P4_ESP32-C6`).
2. Added `set(SDKCONFIG "${CMAKE_BINARY_DIR}/sdkconfig")` to `CMakeLists.txt` (Issue 20).

**Key confirmation log lines (boot, after fix):**
```
Card init success
Identified slave [esp32c6]
Base transport is set-up, TRANSPORT_TX_ACTIVE
```

### Issue 20 — sdkconfig not wiped by fullclean: stale settings persist (RESOLVED)

**Symptom:** Changes to `sdkconfig.defaults` silently have no effect after a `fullclean` + `build` cycle. The old Kconfig values persist in the running firmware.  
**Root cause:** `idf.py fullclean` deletes the `build/` directory only. If `sdkconfig` lives in the project root (the IDF default location), it survives `fullclean`. `sdkconfig.defaults` is only used to seed a **new** `sdkconfig` — once it exists, only missing symbols are filled from defaults. Existing values are never overwritten.  
**Resolution:** Added `set(SDKCONFIG "${CMAKE_BINARY_DIR}/sdkconfig")` to `CMakeLists.txt` before `include(...project.cmake)`. This moves the `sdkconfig` file to `build/sdkconfig`, so `fullclean` always deletes it and every clean build forces full regeneration from `sdkconfig.defaults`.  
**Verification:** After `idf.py fullclean build`, check the compile timestamp in the boot log (`app_init: Compile time:`) against the build log to confirm you are running the freshly built binary before assuming new config took effect.
